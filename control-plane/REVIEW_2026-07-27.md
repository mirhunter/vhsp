## 1. [CRITICAL] A tenant can write arbitrary files on the control-plane host via the backup restore path

`vhsp_ctl/backup.py:923`, in `_fetch_and_verify`:

```python
fetched = workdir / snapshot_name
```

`snapshot_name` is never validated — anywhere. There is no charset
check, no `..` rejection, no "must be a basename" assertion, and no
containment check against `workdir` after joining. I grepped the whole
tree for any such validation and there is none.

Two separate mechanics make this exploitable, both verified against
Python directly rather than assumed:

```
Path('/srv/vhsp/backup/work/restore-123') / '/home/astjohn/.ssh/authorized_keys'
  -> /home/astjohn/.ssh/authorized_keys        # absolute operand REPLACES the base
Path('/srv/vhsp/backup/work/restore-123') / '../../keys/operator_signing_ed25519'
  -> /srv/vhsp/backup/keys/operator_signing_ed25519
```

An absolute `snapshot_name` discards the working directory entirely;
a relative one traverses. Either way the joined path goes straight into
`_fetch_file` (`backup.py:447`), which is a plain `scp` writing to
`str(local_file)` as the control-plane user.

### The reachable path

This is not just an operator-only code path. The chain from a customer's
own panel:

1. A tenant owner opens their panel's **Backups** page and sets
   `dest_host` / `dest_user` / `dest_path` to an SFTP server they
   control. These are stored verbatim — `_reconcile_tenant_backup_config`
   (`backup.py:1212`) writes them into the registry with no validation.
2. They submit a restore. `images/tenant-admin/app.py:4067` takes
   `snapshot_name` from the form with only `.strip()` applied and writes
   it into `backup_request.json` on the shared phpconf volume.
3. The host-side reconciler (`vhsp backup process-requests`, run every
   ~2 minutes by `vhsp-backup-reconcile.timer` as `astjohn`) reads that
   file and calls `restore_backup(tenant.domain, req["restore_snapshot"],
   source="tenant", ...)` at `backup.py:1301`.
4. With `source="tenant"`, the SFTP identity and base path are the
   tenant's own (`backup.py:922`), so the attacker controls both the
   remote server and the content it returns.
5. `scp` writes attacker-chosen bytes to an attacker-chosen absolute
   path on the host, as `astjohn`.

The manifest signature check is real, but it happens *after* the fetch
(`backup.py:942`), so it cannot prevent the write — it only makes the
restore fail afterwards. The `finally: shutil.rmtree(workdir)` doesn't
help either: the file was written outside `workdir`.

### Why it matters

`astjohn` is the control-plane user. It holds passwordless sudo to the
seven wrapper scripts in `deploy/vhsp-sudoers`, and reaches Docker
through the proxy on `127.0.0.1:2375` with `CONTAINERS=1 POST=1 EXEC=1
IMAGES=1`. Writing `/home/astjohn/.ssh/authorized_keys` is the direct
route to a shell as that user, and from there the Docker proxy alone is
root-equivalent on the host (create a container with a host bind mount).
So this is tenant → full platform compromise, crossing the exact trust
boundary the whole architecture is built to hold.

Two lower-effort variants of the same bug, for completeness: overwriting
`/srv/vhsp/backup/keys/operator_signing_ed25519` poisons backup
integrity verification platform-wide, and overwriting
`operator_encryption_age.key` makes every existing encrypted snapshot
permanently undecryptable — a destructive, platform-wide action
triggerable from one tenant's panel.

The same unvalidated value also flows through the operator-facing
routes (`api.py:668`, `mcp_server.py:424`, and web.py's restore
buttons). Those are operator-authenticated so they're a much smaller
concern, but they're the same defect and the fix covers them too.

### Fix

Validate `snapshot_name` at the top of `_fetch_and_verify`, before it is
joined to anything — this is the trust boundary, the same way
`deploy/vhsp-backup-tar` re-validates its own arguments rather than
trusting `backup.py` to have done it:

```python
if snapshot_name != Path(snapshot_name).name or snapshot_name in ("", ".", ".."):
    raise BackupError(f"invalid snapshot name: {snapshot_name!r}")
```

`Path(name).name` collapses any directory component, so the equality
check rejects both traversal and absolute paths in one line. Worth
adding the same assertion in `process_requests` before the call, since
that's where genuinely untrusted input enters the host process. A
belt-and-braces containment check after the join
(`fetched.resolve().parent == workdir.resolve()`) would match the
posture `_safe_webroot_path` already uses in the tenant-admin file
manager, which gets this exact problem right.

## 2. [HIGH] Third-party JavaScript is loaded on the operator admin login page

`vhsp_ctl/web.py:749`, inside the `/login` form body:

```html
<script type="text/javascript"
        src="https://cdnjs.buymeacoffee.com/1.0.0/button.prod.min.js"
        data-name="bmc-button" data-slug="AllenStJohn" ...></script>
```

This is a remote script, loaded from a third-party CDN, executing with
full DOM access on the unauthenticated login page of the highest-blast-
radius surface in the platform — the page where operator credentials are
typed. Anyone who can serve modified content from that origin (a CDN
compromise, a DNS/BGP hijack, or a change made by the widget vendor
themselves) can read the username and password fields directly, or
silently add a listener to exfiltrate them. There is no subresource
integrity attribute, and by design there can't usefully be one on a
widget that expects to update itself.

Nothing else constrains it: there is no `Content-Security-Policy` (the
`_security_headers` hook sets `nosniff`, `X-Frame-Options`, and
`Referrer-Policy`, and deliberately omits CSP for reasons the docstring
explains), so `script-src` is unrestricted.

What makes this stand out is that it contradicts the project's own
settled practice everywhere else. The CodeMirror editor bundle is
vendored into `images/tenant-admin/static/` specifically so nothing is
fetched at runtime, and Swagger UI is vendored into `vhsp_ctl/static/`
for the API docs page. Those decisions were made and documented; this
one script is the only place the rule is broken, and it happens to be on
the worst possible page.

**Fix:** remove it from the login page. If a "buy me a coffee" link is
wanted, put a plain `<a href>` there instead — no script, no third-party
code execution — or move the widget to a page behind authentication
where credentials are never entered. This is a one-line deletion and I'd
treat it as the fastest meaningful risk reduction in the whole review.

## 3. [MEDIUM] Operator-side mailbox management isn't 2FA-gated, which defeats the gate on the bulk route next to it

`vhsp_ctl/web.py:2602`, `/tenants/<domain>/email`, is decorated with
only `@require_auth`. It handles `add`, `reset` (set any mailbox's
password to an operator-chosen value), `delete`, and `quota` for any
tenant's mailboxes.

Meanwhile, in the same file, `/tenants/<domain>/reset-mailbox-passwords`
(line 2056) — the bulk "reset every mailbox" button — *is*
`@require_2fa`. So an operator session with no second factor cannot
press the bulk button, but can achieve the same outcome from the Email
page one mailbox at a time, including resetting `postmaster@`.

This is the same reasoning SECURITY_REVIEW_2 finding #6 applied to the
tenant side, where it was accepted and fixed (the tenant `/email` route
now carries `@require_2fa`). The operator-side equivalent was left
as-is, which leaves the platform in the position of gating the tenant's
own access to their mailboxes more strictly than the operator's access
to everyone's. Email is the recovery channel for most other accounts a
tenant owns, which is what made the original finding worth acting on.

**Fix:** add `@require_2fa` to `tenant_email`, matching both its bulk
counterpart and the tenant-side route. Per `require_2fa`'s own
docstring the CLI remains the escape hatch, so this doesn't risk a
lockout on a fresh install.

## 4. [MEDIUM] No automated tests and no CI anywhere in the project

There is no test file, no `tests/` directory, no `conftest.py`, no
pytest/tox configuration, and no test dependency in `pyproject.toml`.
The only CI workflows are the two Claude ones added today. That's ~18k
lines of Python, shell, and nginx config with zero automated
verification.

The code is unusually well-reasoned and the comments are genuinely
load-bearing — they repeatedly record real bugs found by testing against
live infrastructure ("verified directly," "discovered missing from this
file," "confirmed this was happening"). That's good engineering, but it
means the correctness of this platform currently rests on manual
verification against vhsp2, and it doesn't survive refactoring or a
second contributor.

The highest-value targets are the pure functions where a regression is
silent and security-relevant, all of which are trivially testable with
no Docker or host access:

- `audit.verify_chain` / `_verify_lines` — including the old-format
  entries case its docstring describes.
- `_safe_webroot_path` — traversal, absolute paths, symlink escape.
- `tenant_api_auth.validate_tenant_token` and the operator/tenant
  scope split in `mcp_server._require_operator_access` /
  `_require_tenant_access`. A test asserting that every `@mcp.tool`
  calls exactly one of the two guards would have caught the
  privilege-escalation bug the code comments say was found live during
  that feature's own verification — and would stop it coming back.
- `secretbox` encrypt/decrypt round-trip and the plaintext pass-through.
- `login_throttle` lockout window arithmetic.
- The new `snapshot_name` validation from Finding 1.

A `pytest` job on the workflows already present would cost very little
and would turn the "verified live once" guarantees into standing ones.

## 5. [MEDIUM] Docker socket proxy grants effective root, is unpinned, and this isn't stated as plainly as the sudo scoping is

`deploy/vhsp-docker-proxy.service` correctly zeroes the dangerous
Docker API sections (`SWARM`, `SECRETS`, `CONFIGS`, `NODES`, `BUILD`,
`AUTH`, `SYSTEM`, ...) and the README documents the reasoning well. But
the allowlist keeps `CONTAINERS=1`, `POST=1`, `EXEC=1`, `IMAGES=1`,
`VOLUMES=1`, which together are enough to create a container with a host
bind mount and execute in it — i.e. root on the host. The proxy narrows
the API surface meaningfully, but it does not reduce the privilege level
of anyone who reaches `127.0.0.1:2375`.

That matters for how the other controls are described. `vhsp-sudoers`
is scoped tightly and its header explains that a compromised
`vhsp-admin.service` is refused everything outside the seven wrapper
scripts — but the same compromised process reaches the Docker proxy and
gets root anyway. The sudo scoping is still worth having; it just isn't
the boundary it reads as, and the two documents don't currently say so
in the same place.

Separately, the proxy image is `tecnativa/docker-socket-proxy:latest` —
unpinned. SECURITY_REVIEW_2 #11 noted this and it hasn't changed. For
the one container that mediates all root-equivalent access, a digest pin
is worth more than it is anywhere else in the stack.

**Fix:** pin the image to a digest, and add a sentence to the README's
"Docker socket exposure" section stating that proxy access is
root-equivalent by design, so the sudo scoping isn't read as a stronger
containment guarantee than it is.

## 6. [LOW] WebAuthn login attempts bypass the lockout that TOTP attempts are subject to

`vhsp_ctl/web.py:844`, `webauthn_authenticate_complete`, calls
`login_throttle.record_failure(pending)` on a failed assertion but never
checks `login_throttle.is_locked(pending)` first. The TOTP branch in
`login_2fa` (line 763) does check, and short-circuits.

So a locked-out account can keep attempting the WebAuthn factor, and
each attempt records another failure against a lockout that isn't being
enforced on that path. The practical risk is very low — a WebAuthn
assertion can't be guessed, which is presumably why this went unnoticed
— but it's an inconsistency between two branches of the same gate, and
`login_throttle.record_failure`'s docstring explicitly states its
contract: *"Call only when is_locked() was already False."* This call
site violates that contract.

**Fix:** add the `is_locked` check at the top of
`webauthn_authenticate_complete`, returning the same JSON error shape it
already uses for a failed assertion.

## 7. [LOW] `_fingerprint_public_key` writes the key to a temp file with default permissions

`vhsp_ctl/provisioner.py:1400`, in `_fingerprint_public_key`, uses
`tempfile.NamedTemporaryFile(mode="w", suffix=".pub")`. Python creates
that at 0600, so this is fine as written — noting it only because it's
the one place in the codebase where a key-adjacent file is created
without an explicit `os.chmod` alongside it, unlike every other
sensitive write in `auth.py`, `totp.py`, `webauthn.py`, `secretbox.py`,
`api_auth.py`, and `login_throttle.py`, which all chmod explicitly. It's
a public key, so there's nothing to protect; the value of a comment here
is just to stop a future reader from "fixing" the inconsistency in the
wrong direction.

## What held up well

Areas examined closely that produced no finding:

- **Authorization coverage.** Every one of the ~50 operator routes
  carries `@require_auth`, with `@require_2fa` on the destructive and
  credential-revealing ones. Every one of the 35 MCP tools calls
  exactly one of `_require_operator_access()` / `_require_tenant_access()`
  — verified programmatically, not by eye. The `/self/*` REST routes
  take no domain parameter at all, so a tenant token structurally cannot
  address another tenant.
- **CSRF.** A `before_request` hook on both apps covers every
  state-changing method, uses `hmac.compare_digest`, and the two
  exemptions (the API blueprint, `operator_access_consume`) are each
  correct for the stated reason — bearer-token auth and
  token-as-authentication respectively, neither of which has ambient
  session authority to borrow.
- **Template injection / XSS.** Both apps build pages from
  `render_template_string` over module-level literals; no user-controlled
  value ever becomes template *source*. The `{{ body|safe }}` pattern is
  safe here because the inner pass already escaped, and a `{{ }}`
  surviving inside a rendered value is inert as a variable. The one
  `Markup()` call escapes both interpolations.
- **Path traversal in the tenant file manager.** `_safe_webroot_path`
  resolves first and then checks containment, which defeats encoding
  tricks and planted symlinks. Every mutating route goes through it.
  (This is exactly the check Finding 1's code path is missing.)
- **Shell and SQL injection.** Every `subprocess` and `exec_run` call
  uses list-form argv; no `shell=True` anywhere. The one shelled-out
  string (`_remote_rm`) uses `shlex.quote`. The mariadb statements
  interpolate only registry-derived identifiers and
  `secrets.token_urlsafe` values. SQLite is fully parameterized; the one
  f-string `ALTER TABLE` reads from a hardcoded module constant.
- **The tenant-data → nginx-config boundary.** `images/web/entrypoint.sh`
  re-validates every field it turns into nginx syntax, runs a real
  `nginx -t`, and reverts to last-known-good on failure. The
  `location ~ \.php$` block correctly defends the classic
  `fix_pathinfo` upload-execution class. This is the sharpest piece of
  code in the repo.
- **The root-owned sudo wrappers.** All seven validate their own
  arguments with anchored regexes rather than trusting the caller,
  `vhsp-backup-tar` resolves with `realpath -m` before its containment
  check, and `vhsp-mcp-firewall` hardcodes the port rather than
  accepting one.
- **Destructive-action confirmations in both UIs.** Every destroy /
  reset / remove / revoke form carries an `onsubmit="return confirm(...)"`,
  including both 2FA-removal forms. My first automated pass suggested
  gaps here; they were an artifact of my own pattern, and re-checking
  each one directly found them all present.

## Closing note

The security engineering here is genuinely strong, and the prior two
reviews were acted on properly rather than filed. Findings 2 through 7
are all small and mostly consistency issues — a rule the codebase
already follows everywhere else, not applied in one spot.

Finding 1 is different in kind. Every other input boundary in this
project is defended twice: the tenant-admin file manager resolves and
checks containment, the sudo wrappers re-validate arguments their
callers already validated, `images/web/entrypoint.sh` re-checks every
value tenant-admin already checked. `snapshot_name` is the one
tenant-controlled string that reaches a privileged host operation with
no validation at either end, and it happens to reach a filesystem write.
It should be fixed before the next tenant is onboarded; the fix is two
lines and needs no design decision.
