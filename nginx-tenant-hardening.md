# Tenant-panel gaps: nginx-level hardening controls

Found while dogfooding one real tenant (`tenant2.example.com`, currently running WordPress, installed via SFTP-only access, no shell) as a usability/security test of VHSP. **WordPress is just the tenant that happened to be under test — none of this should be read as WordPress-specific.** The underlying issues are about what a PHP-FPM tenant's runtime can reach, and about response-header fingerprinting in general; the next tenant onboarded might be hand-written code, Drupal, a Node/Python/Ruby app, or anything else, and most of these gaps apply just as much (or, for the UID issue, apply to *any* language runtime the platform ever offers, not just PHP). Examples below use WordPress paths only because that's what was on hand to test against — treat them as illustrative, not as the scope.

These are protections that live at the nginx layer, which a tenant has no way to reach from inside their own container — they either need to be a tenant-panel-controllable setting, or a platform-wide default applied at provisioning time. Right now they're neither.

## Why this matters more than it might look like from a single WordPress test

Confirmed directly on this tenant: PHP-FPM's effective UID/GID (`getmyuid()`/`getmygid()`) is **identical** to the UID/GID that owns every file in the tenant's webroot — the same account used for SFTP access. This was verified, not assumed (a diagnostic script compared `getmyuid()` against `fileowner()` on `wp-config.php` and they matched exactly: `1000`/`100`).

Practical consequence, stated generally: any executable file that ends up running anywhere in a tenant's writable tree — regardless of language/runtime, however the file got there — has exactly the same read/write reach across that tenant's entire webroot that the tenant's own SFTP session has. There's no extra wall between "a webshell/malicious script is now running" and "full compromise of everything in this container's webroot, config/secrets files included," beyond whatever prevented the file from executing in the first place. That makes web-server-level execution controls (not just an interpreter-level toggle like PHP's `disable_functions`) the load-bearing protection here — and it applies to whatever runtime a given tenant is on, not just PHP. None of the below are currently tenant-configurable or applied by default.

## Status: all four items below now resolved

- **Code execution in upload/writable directories**: fixed. `images/web/entrypoint.sh`'s `write_tenant_nginx_conf` now emits a `location ~* ^/(<dirs>)/.*\.php$ { deny all; }` block from a tenant-declared `noexec_dirs.txt` — exactly the "tenant-declared list" shape this doc suggested, rather than a hardcoded WordPress-shaped path. Self-service page lives in `images/tenant-admin/app.py` (`/noexec-dirs`). Re-validated a second time in the entrypoint (not just tenant-admin) before being turned into nginx regex syntax, same trust-boundary pattern as the other tenant-panel-writable nginx config.

- **Runtime version-fingerprinting headers**: fixed. `fastcgi_hide_header X-Powered-By;` is in `images/web/nginx.conf`'s PHP location block, and `expose_php = Off` is set platform-wide in the Dockerfile (`/etc/php83/conf.d/99-vhsp-security.ini`) — belt-and-suspenders, not tenant-configurable (there's no legitimate reason a tenant would want this on). `server_tokens off` behavior confirmed unchanged.

- **`fastcgi` PATH_INFO handling**: fixed. `images/web/nginx.conf`'s `location ~ \.php$` block has `try_files $uri @php_not_found;` ahead of `fastcgi_pass`, closing the `/uploads/photo.jpg/x.php` RCE class directly in the base template (applies to every tenant, not opt-in). Updated 2026-07-23: the fallback target changed from a bare `=404` to a named `@php_not_found` location that does `return 301 /;` — nonexistent `.php` paths (near-100% vulnerability-scanner noise: old `xmlrpc.php` exploits, `wp-config.php.bak` probes, etc.) now get a clean redirect to the homepage instead of nginx's default 404 page, while genuine no-extension content misses still get WordPress's own themed 404 via `@fallback` untouched. Verified the `noexec_dirs` block (previous item) still takes precedence for declared upload dirs — it's `include`d earlier in the file, so nginx's first-match regex-location ordering means a `.php` request under a noexec dir still hits `deny all` (403) and never reaches this new fallback at all. Rebuilt `vhsp-web:latest` and rolled out via `recreate_web.py` to the one live tenant. Known follow-up, not yet fixed: the `Location` header on this (and every other nginx-level `return 301`, including the tenant-panel's own custom-redirects feature) comes back `http://` not `https://`, since this container only ever terminates plain HTTP internally behind two proxy hops and nginx's own `$scheme` reflects that -- the swarm's outer Traefik redirects it back to `https://` as a harmless extra hop today, but the right fix would be trusting `X-Forwarded-Proto` into `$scheme` the same way `vhsp-realip.conf` already recovers the real client IP.

- **Login/auth-endpoint brute-force protection**: confirmed active, no code change needed. Checked the swarm's actual Traefik config directly (`/docker/traefik/traefik.yml` + `conf/crowdsec.yml` on the node fronting `tenant2.example.com`): the CrowdSec bouncer plugin is applied at the `websecure` (443) **entrypoint** level, not per-router — so it's automatically in the path for every HTTPS router on that Traefik instance, `tenant2.example.com`'s included, with plain HTTP force-redirected to HTTPS so nothing bypasses it. The bouncer's log showed a month-old (2026-06-22) stretch of `appsecQuery:unreachable` errors, but that log hasn't been written since, and both the CrowdSec LAPI (8080) and AppSec (7422) ports are reachable from the Traefik node right now with no recent errors in Traefik's own logs — that outage looks resolved, not ongoing. No per-tenant or per-framework work needed here; the shared-edge design already generalizes the way architecture.md intended.

## Already working, no action needed

- The tenant-panel's **"fall back to index.php / index.html on 404"** setting works correctly and is required for any front-controller-style app (WordPress, Drupal, most PHP frameworks, plenty of non-PHP frameworks too) to function at all under nginx — there's no `.htaccess` equivalent, so this setting is the *entire* web-server-level routing story for such an app, not an optional nicety. Confirmed this is what makes pretty permalinks, the REST API, etc. work once permalinks were switched off "Plain" for this particular (WordPress) tenant, but the setting itself isn't WordPress-specific. No change needed, just noting it as context for whoever picks up the items above, since it's adjacent territory (nginx-level request routing for tenant apps generally).

## Fix shape that was used

Followed the pattern already established elsewhere in the platform (PHP `disable_functions` toggle with a self-service opt-out): **secure by default** (noexec-dirs pattern denies execution unless a tenant explicitly lists the directory; header/PATH_INFO fixes are unconditional, no opt-out at all since there's no legitimate reason to want them off) **with a tenant-panel control where a real self-service need existed** (which directories count as "writable, never code" is inherently tenant-specific, so that one's a tenant-declared list rather than a hardcoded WordPress-shaped path — the other three items apply uniformly to every tenant on this stack and needed no per-tenant control).
